Überblick

In diesem Artikel zeige ich, wie ein vSAN Cluster in VMware Cloud Foundation 9.1 über zwei Availability Zones (AZ1 und AZ2) “ge-stretched” werden kann. Grundlage ist die SDDC Manager API.

Voraussetzungen

Vor dem Start müssen folgende Bedingungen erfüllt sein:

  • Mindestens 3 Hosts müssen sich im Status commissioned befinden.
  • Die ESX-Hosts in AZ2 müssen dieselbe vmnic-zu-vDS-Zuordnung verwenden wie die vorhandenen Hosts in AZ1.
  • vCenter muss betriebsbereit sein.
  • Das Planning and Preparation Workbook muss für die Management- oder Workload-Domain ausgefüllt sein.
  • Alle Anforderungen aus der Prerequisite Checklist des Workbooks müssen erfüllt sein.
  • Es muss eine gleiche Anzahl von Hosts pro Availability Zone vorhanden sein, um ausreichende Ressourcen bei einem vollständigen AZ-Ausfall zu gewährleisten.
  • Ein vSAN Witness Host muss deployed und konfiguriert sein.
  • Beim Stretchen eines Clusters in einer Workload Domain muss der Standard-Management-vSphere-Cluster bereits gestretcht sein.

Hinweis: Ein Cluster kann in folgenden Fällen nicht gestretcht werden:

  • Der Cluster teilt eine vSAN Storage Policy mit einem anderen Cluster.
  • Der Cluster enthält DPU-backed Hosts.
  • Hosts innerhalb einer Availability Zone befinden sich in unterschiedlichen Subnetzen (L3).
  • vSphere Supervisor ist auf dem Cluster aktiviert.

Weitere Designanforderungen und -empfehlungen sind im Abschnitt Stretched vSAN Storage Model der offiziellen VMware-Dokumentation beschrieben.

Schritt 1 – Network Pool für AZ2 erstellen

Pfad: vCenter → Global Inventory → Network Pools → Create Network Pool

Feld Wert
Network Pool Name Name-AZ2
Network Type vSAN, vMotion
VLAN ID <AZ2-VLAN-ID>
MTU <MTU-Wert>
Gateway (CIDR) <Gateway-IP/Prefix>
IP Address Ranges <Start-IP> bis <End-IP>

Schritt 2 – vDS für AZ2 vorbereiten

Auf dem vDS Switch müssen neue Port Groups (PGs) für AZ2 angelegt werden:

  • ESX Management
  • vMotion
  • vSAN

Schritt 3 – Hosts in Betrieb nehmen (Commission Hosts)

Pfad: vCenter → Global Inventory → Hosts → Unassigned Hosts → Commission Hosts

Alle erforderlichen Informationen ausfüllen und den in Schritt 1 erstellten Network Pool für AZ2 auswählen.

Schritt 4 – ESX Host IDs der unkonfigurierten Hosts abrufen

Pfad: SDDC Manager API → VCF Operations → Build → Developer Center → APIs & SDKs → SDDC Manager API Explorer

GET /v1/hosts

Im Feld status den Wert UNASSIGNED_USEABLE eintragen und Execute klicken. Die zurückgegebenen Host IDs für den nächsten Schritt notieren.

Schritt 5 – Cluster ID abrufen

GET /v1/clusters

Nach dem Ausführen in der Antwort zu PageOfCluster navigieren und das Feld id des Zielclusters kopieren.

Schritt 6 – JSON-Spezifikation erstellen

Hinweis: witnessTrafficSharedWithVsanTraffic erklärt

Dieser Parameter steuert, welcher VMkernel-Adapter auf den Daten-Nodes für die Kommunikation mit dem vSAN Witness Host verwendet wird.

Wert Verwendeter VMkernel Einsatzszenario
true VMK vSAN (vSAN VMkernel-Adapter der Daten-Nodes) vSAN- und Witness-Traffic teilen dasselbe Netzwerksegment.
false VMK0 (Management VMkernel-Adapter) Der Witness Host ist nur über das Management-Netzwerk erreichbar.

Schritt 7 – JSON-Spezifikation validieren

  1. Im SDDC Manager API Explorer zu Clusters → POST /v1/clusters/{id}/validations navigieren.
  2. Im Feld Value die in Schritt 5 ermittelte Cluster ID eintragen.
  3. Im Feld clusterUpdateSpec folgendes eingeben:
{
  "clusterUpdateSpec": <JSON-Spezifikation aus Schritt 6>
}
  1. Execute klicken und im Bestätigungsdialog auf Continue klicken.
  2. In der Response den Abschnitt result aufklappen und prüfen, dass der Status SUCCEEDED lautet.

Schritt 8 – Cluster stretchen

  1. Im SDDC Manager API Explorer zu Clusters → PATCH /v1/clusters/{id} navigieren.
  2. Die Cluster ID in das Feld Value einfügen.
  3. Die JSON-Spezifikation (Template 1 oder 2) in das Feld clusterUpdateSpec einfügen.
  4. Execute klicken und im Bestätigungsdialog auf Continue klicken.

Den Fortschritt des Stretch-Cluster-Vorgangs kann unter Fleet Management → Tasks verfolgt werden.
